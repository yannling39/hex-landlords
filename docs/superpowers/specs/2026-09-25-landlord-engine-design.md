# 斗地主底层逻辑设计规格

## 目标

在当前空仓库中建立可运行的 TypeScript 斗地主规则引擎。今天的交付目标是通过命令行自动跑完普通斗地主 Run；一个 Run 按 GDD v1.2 包含三手牌，由三个本地规则型 AI 驱动，以验证发牌、叫地主、牌型、牌权、倍数和结算闭环。

本阶段不做 UI、网络服务器、账号或海克斯效果。结构必须允许后续由同一个 Node.js 进程作为房主服务器，通过 WebSocket 接受玩家命令并广播过滤后的状态。

## 已确认约束

- 语言为 TypeScript，运行时为 Node.js，使用 npm 管理脚本和开发依赖。
- 规则模块不得依赖 DOM、浏览器 API、React 或网络传输。
- 规则操作采用序列化 `Command` 输入和 `Event` 输出。
- 随机数来源在创建 Run 时注入；支持固定种子，便于复现问题。初始化时预生成每手及最多两次全员不叫重发所需的牌局分配，规则 reducer 本身不调用随机数。
- 游戏规则状态可 JSON 序列化；随机数生成器本身不放入传输状态。
- 服务端将来是牌局唯一权威；客户端提交命令，不提交新状态。
- 向联机客户端发送数据前必须调用玩家视图投影，绝不把完整状态或其他玩家手牌发给客户端。
- 海克斯阶段只保留 HAND_END 到 NEXT_HAND 的扩展挂点，默认关闭，不影响今天的普通斗地主流程。

## 本阶段行为范围

### 牌和发牌

- 一副标准 54 张牌，以唯一 `CardId` 区分花色和点数。
- 点数顺序为 3 到 A、2、小王、大王；花色不参与牌力比较。
- 每手发给 A、B、C 各 17 张，剩余 3 张为底牌。
- 使用 Fisher-Yates 洗牌；随机数生成器支持种子注入。
- 同一牌局中不得产生重复牌、丢牌或凭空造牌。

### 叫地主

- 首叫玩家开始，按 A、B、C 环形顺序叫 0、1、2 或 3 分。0 表示不叫；非 0 分必须高于当前最高叫分。
- 叫到 3 分立即确定地主。三人均不叫则重新洗牌发牌；最多重新发两次，第三次仍全不叫时由本次首叫玩家成为地主，底分为 1。
- 地主获得三张底牌并先出牌。农民为另外两名玩家。
- Run 内每手首叫玩家依次轮换 A、B、C。

### 牌型与比较

支持 GDD v1.2 列出的单张、对子、三张、三带一、三带二、顺子、连对、飞机带单、飞机带对子、四带二带单牌、四带二带对子、炸弹和王炸。

- 顺子至少 5 张；连对至少 3 对；飞机至少 2 个连续三张。连续序列仅能使用 3 到 A，不含 2 和王。
- 三带一的附带牌必须是一张三张主体以外的牌；三带二必须带一对。
- 飞机带单要求每个主体三张附带一张非主体牌；附带牌可组成对子，但不能再组成三张。
- 飞机带对子要求 N 个连续三张主体带 N 对对子；带牌对子点数互不相同，且不能与飞机主体点数重叠。MVP 最短为两连飞机，例如 `333444 + 55 + 66`。
- 四带二带单牌要求四张主体以外恰好两张牌；两张附带牌允许同点数。
- 四带二带对子要求四张主体以外恰好两对对子；两对点数不同，且不能与四张主体点数重叠。例如 `7777 + 99 + JJ`。
- 四带二带单牌与四带二带对子是不同牌型，不能互相压制；各自按四张主体点数比较。
- 普通牌只可压同牌型且同长度、主体牌力更高的牌。炸弹压普通牌并按炸弹点数比较；王炸最大。
- 牌型识别返回标准化结构：类别、主体点数、序列长度、附带牌数和带牌模式。识别和比较位于同一领域模块，不由 UI 或 AI 重复实现。
- 若手牌中有多种方式能组成所选牌型，合法性检查按“所提交的精确牌集合”判断；比较只使用该牌型的主体，不比较附带牌。

### 出牌、Pass 与结束

- 每个动作由当前行动玩家提交。领出时必须出牌，不能 Pass。
- 跟牌时可以提交能压过桌面牌的合法牌型，或 Pass。
- 最后一次有效出牌后，连续两名其他玩家 Pass 时，最后出牌者赢得当前墩并获得下一墩领出权；Pass 计数随墩重置。
- 出牌后手牌为空时立即结束本手，不再等待其他玩家响应。
- 地主先出完则地主方胜；任一农民先出完则农民方胜。
- 每个 Run 三手；首叫玩家轮换，分数累加。单手地主赢得 `2 * 底分 * 倍数`，每名农民各扣 `底分 * 倍数`；地主失败时反向结算。每打出一个炸弹或王炸，倍数乘 2。
- MVP 不实现春天、反春天、加倍或海克斯效果。

## 规则边界说明

GDD v1.2 将“飞机带单”和“四带二”写为受限 MVP 牌型，但没有完整规定主体枚举、带牌重复点数和多种解释下的选择方式。本规格明确允许飞机单牌带牌组成对子但不允许三张；另支持飞机带对子，以及四带二带两张单牌和带两对对子两种独立牌型。飞机带对子和四带二带对子都要求带牌点数彼此不同且不与主体重叠。实现必须通过固定测试案例锁定该约定。

叫地主的重发次数、首叫位轮换和 Run 计分延续 GDD v1.2。展示底牌的 UI 确认动作属于 UI 阶段；命令行演示在地主确定后自动进入出牌阶段。

## 技术结构

```text
src/domain/
  card.ts          Card、CardId、点数和花色
  random.ts        可注入的随机源和种子实现
  deck.ts          54 张牌、洗牌、发牌
  pattern.ts       牌型解析和规范结构
  compare.ts       同型比较和压制关系
  bidding.ts       叫地主合法性与转移
  game.ts          JSON 可序列化权威状态和 reducer
  commands.ts      外部动作联合类型
  events.ts        领域事件联合类型
  player-view.ts   面向单个玩家的隐藏信息过滤
  scoring.ts       单手与 Run 结算
  ai.ts            只基于自身手牌和公开信息生成命令
src/cli/demo.ts    自动跑完三手 Run 并打印日志
tests/             Node test runner 测试
```

核心接口草案：

```ts
type Command =
  | { type: 'BID'; playerId: PlayerId; score: 0 | 1 | 2 | 3 }
  | { type: 'PLAY'; playerId: PlayerId; cardIds: CardId[] }
  | { type: 'PASS'; playerId: PlayerId };

type Transition = {
  state: GameState;
  events: GameEvent[];
  error?: RuleError;
};

function dispatch(state: GameState, command: Command): Transition;
function viewForPlayer(state: GameState, playerId: PlayerId): PlayerView;
```

`dispatch` 是纯状态转移：不读系统时间、不生成随机数、不做 IO。随机种子只用于创建牌局和洗牌；AI 在引擎外根据玩家视图选择命令。拒绝的命令返回稳定错误码，并保持原状态不变。

Run 初始化器使用注入的随机源预生成三手各自的初始发牌和最多两次重发牌；领域状态可包含这些私有待发牌数据以保持 reducer 确定性，但 `PlayerView` 必须过滤未公开的当前手牌、重发牌和未来牌局数据。

未来联机的服务端包装层可复用 `dispatch`：验证连接身份对应的 `playerId`，调用规则引擎，保存新状态和递增事件序号，再分别向每位客户端发送 `viewForPlayer` 与公开事件。此服务端包装层不属于本阶段。

## 错误和隐藏信息

- 非当前行动玩家、非法叫分、非法牌型、不能压过当前牌、无桌面牌时 Pass、已结束牌局提交动作都返回明确错误码。
- 失败命令不得修改手牌、分数、牌权或任何牌局状态。事件序号由未来服务端包装层维护，随机数只在创建牌局时使用。
- 完整 `GameState` 是本地引擎内部状态；未来网络边界只能使用 `PlayerView`。
- 玩家视图包含自己的手牌、其他玩家手牌数、公开叫分/底牌/桌面牌/分数/当前行动方，不包含他人手牌或未来牌堆顺序。

## 验收

- `npm run build` 成功。
- `npm test` 成功，覆盖牌组守恒、洗牌复现、发牌、叫地主、所有牌型（含飞机带对子和四带二带对子）及压制、Pass/牌权、错误命令原子性、计分、玩家视图隐藏信息。
- `npm run demo` 以固定种子让三名 AI 自动完成一个三手 Run，打印叫地主、公开出牌、Pass、倍数和结算；不得打印尚未公开的 AI 手牌或剩余牌堆。
- 连续运行 demo 多次结果一致，不死循环。
- 海克斯关闭时状态正常从 HAND_END 进入 NEXT_HAND；无具体强化效果。
- 代码不实现网络传输，但核心状态、命令、事件和玩家视图可 JSON 序列化。

## 不在范围

浏览器界面、WebSocket、房间管理、NAT 穿透、房主迁移、持久化数据库、登录、匹配、完整桌规变体、复杂 AI、春天/反春天、加倍和海克斯强化池。
